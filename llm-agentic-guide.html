Foundations
Start here

From tokens to a working model

The chain is: text → tokens → embeddings → transformer layers → next-token prediction, repeated at scale until capability emerges. Everything downstream — RAG, agents, evaluation — is scaffolding built around this one core loop.

Tokens, not words

Models never see letters or whole words directly. Text is split into subword pieces by a tokenizer (commonly byte-pair encoding), and the model operates entirely on those piece-IDs.

Embeddings

Each token ID maps to a vector — a point in high-dimensional space where distance and direction encode meaning. This same mechanism resurfaces later, unchanged, as the backbone of retrieval.

Why transformers over RNNs

Self-attention lets every token look at every other token in one step, in parallel — RNNs had to pass information sequentially, which made long-range dependencies slow to learn and slower to train.

Pretraining, plainly

The entire base model is trained on one task: predict the next token. Scaling data, parameters, and compute together produces roughly predictable improvement — this is what "scaling laws" refers to.

Nuance

Emergent capability may be partly a measurement artifact. Smooth, continuous improvement in the underlying loss can look like a sudden jump in capability purely because of how a benchmark scores answers — right/wrong is discontinuous even when the model's certainty was rising gradually beneath it.

From base model to assistant

A freshly pretrained model completes text — it doesn't follow instructions. Instruction tuning teaches it to respond to commands; RLHF or DPO then aligns its outputs with what humans actually prefer. This two-step process is the difference between a raw next-token predictor and something that behaves like an assistant.

Nuance

Alignment optimizes for preference, not truth. A reward model trained on "which answer do people like better" will happily learn that confident, agreeable answers score higher than correct-but-unwelcome ones — this is the mechanical root of sycophancy, not a separate bug bolted on top.

Where it gets strange

Tokenization & attention nuances

Illustrative simulation only — a simplified mock splitter, not a real production tokenizer. The point it demonstrates is real: the model reasons over these chunks, not over individual letters, so "count the r's in strawberry" requires indirect reasoning about pieces it never directly inspected.

Same root cause, many symptoms

Poor letter-counting, weak string reversal, shaky arithmetic on long numbers, and inconsistent rhyming with rare words all trace back to the same thing: no direct character-level access.

Tokenization is not language-neutral

English text tokenizes efficiently; many other languages fragment into far more tokens per sentence — meaning worse effective context length and higher cost for an equivalent amount of meaning.

Lost in the middle

Retrieval accuracy across a long context is not flat — models attend well to the very start and very end, and measurably worse to facts buried in the middle, regardless of the context window's advertised size.

Effective context < advertised context

A "1M token window" passing a single needle-in-haystack test says little about multi-hop tasks that require connecting several scattered facts across that same window — that's a much harder, separately-measured failure mode.

Strange but true

Temperature 0 is not fully deterministic in practice. Floating-point non-associativity across batched GPU execution means identical prompts at temperature 0 can still occasionally return different completions from the same API — determinism is closer to "very likely," not guaranteed.

Strange but true

Prompt caching rewards stable prefixes. Providers that cache repeated context charge less for tokens that appeared identically in a prior call — which means where you place the variable part of a prompt (end, not beginning) directly affects cost, independent of content.

Intermediate
Knowledge limits

Retrieval-augmented generation

The pipeline: chunk documents → embed chunks → store in a vector index → embed the query → retrieve nearest chunks → stuff them into the prompt. Same embedding mechanism from Foundations, now applied to search instead of model input.

Chunking strategy matters more than the model

Fixed-size, recursive, and semantic chunking produce meaningfully different retrieval quality on the same documents — this is usually the highest-leverage tuning knob in a RAG system, and the most neglected one.

Hybrid search

Pure vector similarity misses exact keyword matches (names, IDs, codes). Combining BM25 keyword search with vector search, then reranking, typically beats either alone.

Rerankers

A cross-encoder reranker scores query-chunk pairs jointly (slower, more accurate) after a fast initial vector retrieval narrows the field — a two-stage retrieve-then-rerank pipeline is now closer to standard practice than an optional extra.

RAG-specific evaluation

Faithfulness (does the answer only use retrieved content), context precision, and context recall are measured separately — a fluent, well-cited-looking answer can still fail all three.

Why RAG still hallucinates

Retrieval gives you relevant chunks, not sufficient chunks. If the retrieved context doesn't fully answer the question, the model fills the gap with something plausible-sounding rather than saying so — retrieval reduces hallucination, it doesn't eliminate it.

Why RAG still hallucinates

Embedding similarity ≠ factual relevance. A chunk can sit close in vector space while actually answering an adjacent, different question — the model then confidently blends or misapplies it.

Why RAG still hallucinates

Conflicting or redundant chunks get blended. If two retrieved passages disagree (an old policy doc and its update, say), the model can synthesize a plausible-sounding answer that neither source actually states.

Intermediate → Expert
Static answers → actions

Tool use & agent loops

A tool call is a single action: the model emits structured intent, code executes it, the result feeds back in. An agent is what happens when that becomes a loop — plan, act, observe, replan — with memory tracking state across steps.

ReAct pattern

Interleave reasoning traces with actions ("Thought → Action → Observation") rather than reasoning silently then acting once — this measurably reduces compounding errors on multi-step tasks.

Reflexion / self-critique loops

Adding an explicit self-critique step after a failed attempt, then retrying with that critique in context, tends to outperform simply retrying the same action.

Plan-and-execute vs. reactive

Reactive agents decide one step at a time (flexible, but can wander). Plan-and-execute agents commit to a multi-step plan upfront, then execute it (more predictable, but brittle if the plan was wrong).

Tool schema design

Vague tool descriptions and overlapping tool purposes are a leading cause of wrong tool selection — this is a prompt-engineering problem wearing an API costume.

Agent-specific strangeness

Tool-output hallucination. If a real tool result isn't clearly delimited from the model's own generated text in context, the model can "continue" a plausible-looking fake result instead of waiting for the actual one — a formatting problem that looks like a reasoning failure.

Use the ReAct pattern: on each step, output a Thought, then an Action (one tool call), then wait for the Observation before continuing. Stop and ask for clarification after 3 consecutive failed tool calls rather than retrying indefinitely.
Expert
One agent → many

Multi-agent systems

Complex tasks get split across specialized agents — a planner, a coder, a critic — that hand work to each other rather than one agent doing everything in one long loop.

Orchestrator–worker

One agent decomposes the task and dispatches subtasks to worker agents, then assembles their results — good for parallelizable, well-scoped subtasks.

Debate / voting

Multiple agents independently attempt the same task, then a judge (or majority vote) selects the best answer — trades cost for reliability on ambiguous tasks.

Shared vs. isolated context

Shared context between agents avoids repeated re-explaining but risks one agent's error contaminating all of them; isolated context is more robust but costs more in redundant setup.

Agent-to-agent protocols

Standardized handoff formats (context, task, and tool-access exchanged in a defined shape rather than free-form text) are what let agents built by different teams or vendors interoperate at all.

Nuance

More agents ≠ more reliability. Every additional handoff is another point where context can be dropped, misread, or subtly altered — multi-agent systems often need more evaluation and tracing per task, not less, to be trustworthy.

Evaluation & guardrails

LLM-as-judge bias

A model judging outputs — including its own family's outputs — tends to show self-preference bias, and in pairwise comparisons, whichever answer is shown first often gets a small unearned edge.

Benchmark contamination

If benchmark questions leaked into pretraining data, a high score reflects memorization, not capability — this is why held-out, frequently-refreshed evals matter more than a single static leaderboard number.

Prompt injection via retrieved content

Injection doesn't require a malicious user — a poisoned web page or document pulled in by RAG or a browsing tool can carry instructions the model treats as legitimate, unless retrieved content is explicitly untrusted by design.

Structured-output tax

Forcing strict JSON-schema-constrained decoding can measurably degrade reasoning quality on harder tasks — sometimes it's better to let the model reason freely first, then parse structure out afterward.

Nuance

Inverse scaling exists. A handful of tasks get worse, not better, with more scale or more RLHF — larger, more aligned models can become more confidently wrong or more sycophantic on specific tasks, not uniformly more capable.

What didn't survive contact with reality

The graveyard

Useful judgment often comes from knowing what was tried and abandoned, not just what shipped.

Fully unconstrained autonomous agents

Early "give it a goal and let it run indefinitely" agents tended to wander, loop, or burn budget on self-invented subtasks with no real stopping condition — task decomposition with explicit checkpoints replaced this pattern.

Pure symbolic planners for open-domain tasks

Rigid, hand-coded planning worked for narrow domains but couldn't handle the ambiguity of real-world instructions — this is most of why LLM-based planning displaced it for general-purpose agents.

One giant prompt instead of retrieval

Stuffing an entire knowledge base into context worked briefly at small scale, then hit cost and lost-in-the-middle limits — RAG exists largely because this doesn't scale.
